# 책장 스캐너 (find_my_book)

**내 책장을 앱 안에 그대로 옮긴다.** 실제 책장과 같은 칸 수로 맞춰 두고, 칸마다 사진을 찍으면
그 칸에 꽂힌 책이 실제 순서 그대로 앱 책장에 들어선다. 책을 옮기거나 빼면 앱에서도 옮기고 뺀다.

인식은 오픈소스 OCR인 [tesseract.js](https://github.com/naptha/tesseract.js)로
**브라우저 안에서** 처리합니다. 서버도, API 키도, 사진 업로드도 없습니다.

자세한 시나리오와 완료 기준은 [docs/시나리오.md](docs/시나리오.md),
UX 점검과 개선 기록은 [docs/ux-점검.md](docs/ux-점검.md)에 있습니다.

## 화면 흐름

1. **책장 설정** — 왼쪽에서 가로·세로 칸 수를 조절하면 오른쪽 미리보기가 바로 따라 바뀝니다.
   기본은 가로 8 × 세로 2입니다. 실제 책장과 같은 칸 수로 맞춰 주세요.
2. **책장 화면** — 만든 책장이 늘 보입니다. 칸에 꽂힌 책은 사진에서 뽑은 색과 두께로 그려져
   실제 책장과 닮아 보입니다.
3. **칸 채우기** — 칸을 누르고 [이 칸 촬영하기]로 그 칸만 찍습니다. 책이 빽빽해 책등이
   얇게 잡히면 [이어서 찍기]로 나눠 찍기를 권합니다. 인식이 끝나면 왼쪽부터의
   순서 그대로 보여 주고, [이 칸에 넣기]를 누르면 그 칸이 채워집니다.
4. **손보기** — 제목·저자 고치기, 순서 바꾸기(← →), 빼기(×), 책 추가, 다른 칸으로 옮기기.
   같은 칸을 다시 찍으면 내용이 교체됩니다. 빼기·비우기·교체는 **되돌리기**가 딸려 옵니다.
5. **여러 책장** — 거실·서재처럼 책장을 여러 개 두고 위쪽에서 전환합니다.

모든 변경은 즉시 브라우저에 저장되고, CSV로 내보내면 어느 칸 몇 번째 책인지까지 남습니다.

## 실행

```bash
npm install
npm run dev      # http://localhost:5173
```

빌드해서 아무 정적 호스팅에나 올려도 됩니다. 백엔드가 필요 없습니다.

```bash
npm run build
npm run preview
```

### 완전 오프라인으로 쓰기

기본값에서는 언어 데이터만 처음 한 번 공개 CDN에서 받아 옵니다.
영어 2.8MB, 한국어 1.5MB, 세로 한글 0.6MB이고, 쓰는 언어의 것만 받습니다.
이 기본 경로는 브라우저에서 실제로 받아 인식되는 것까지 확인했습니다.
그것마저 없애려면 미리 받아 두고 경로를 바꿔 주세요.

```bash
npm run fetch:langdata            # public/tessdata 에 eng, kor 저장
VITE_TESSDATA_PATH=/tessdata npm run build
```

OCR 워커와 wasm 코어는 이미 앱과 함께 배포됩니다. `npm install` 뒤 빌드할 때
`scripts/copy-tesseract-assets.mjs`가 `public/tesseract`로 복사합니다.

언어 데이터를 못 받으면(오프라인이거나 CDN이 막힌 경우) 화면에 그 사실과 함께
위 명령을 안내합니다. 기다리다 멈춰 있지 않습니다.

## 배포

서버가 필요 없습니다. OCR 이 전부 브라우저에서 도니 빌드 결과물만 올리면 됩니다.

### GitHub Pages (설정돼 있음)

`main` 에 올라오면 `.github/workflows/deploy.yml` 이 빌드해서 배포합니다.
**저장소에서 한 번만** Settings → Pages → Source 를 **GitHub Actions** 로 바꿔 주세요.

주소는 `https://<사용자>.github.io/<저장소 이름>/` 이 됩니다. 하위 경로라 자산 경로가
어긋나기 쉬운데, 워크플로가 저장소 이름을 `VITE_BASE` 로 넣어 줍니다. 이름을 바꿔도 따라갑니다.

### 다른 곳에 올릴 때

Cloudflare Pages, Netlify, Vercel 모두 무료로 됩니다. 빌드 명령은 `npm run build`,
배포할 폴더는 `dist` 입니다. 최상위 도메인으로 서비스한다면 `VITE_BASE` 는 건드릴 필요가 없고,
하위 경로라면 `VITE_BASE=/경로/` 를 넣고 빌드하세요.

```bash
VITE_BASE=/find_my_book/ npm run build   # 하위 경로에 올릴 때
npx vite preview --base=/find_my_book/   # 같은 경로로 확인
```

배포물은 12MB 정도입니다. 대부분 wasm 코어 세 종류(각 3.7MB)이고 브라우저는 그중
하나만 받습니다. 언어 데이터는 처음 한 번 CDN 에서 받습니다. 첫 방문이 느린 대신
그 뒤로는 캐시에서 씁니다.

CDN 조차 쓰지 않으려면 위의 "완전 오프라인으로 쓰기" 를 따르되, **하위 경로에 올릴 때는
경로에도 하위 경로를 붙여야 합니다.** 루트 기준으로 적으면 브라우저가 엉뚱한 곳을 찾습니다.

```bash
npm run fetch:langdata
VITE_BASE=/find_my_book/ VITE_TESSDATA_PATH=/find_my_book/tessdata npm run build
```

### 휴대폰에서 카메라 쓰기

브라우저는 `localhost`가 아닌 주소에서 **HTTPS일 때만** 카메라를 열어 줍니다.
휴대폰에서 테스트하려면 터널로 HTTPS 주소를 만들어 접속하세요.
카메라를 못 여는 환경에서는 **사진 선택** 버튼으로 갤러리 사진을 씁니다.

## 어떻게 읽는가

사진 한 장을 통째로 OCR에 넣으면 옆 책 글자가 한 줄로 섞여 읽힙니다.
그래서 책등을 먼저 나눈 뒤 한 권씩 읽습니다.

1. **선반 안쪽 찾기** — 책이 실제로 꽂힌 행 구간을 먼저 자릅니다. 한 칸만 찍어 달라고
   안내해도 위 칸 천장과 아래 칸이 같이 찍히는데, 그대로 두면 아래 칸 책의 경계가
   위 칸 경계와 뒤섞여 둘 다 놓칩니다. 단서는 **줄마다의 색 폭**입니다. 여러 책이 걸친 줄은
   색이 제각각이고, 나뭇결 벽이나 빈 선반은 한 색입니다. 에지 양만 보면 무늬 없는 책등이
   배경처럼 보여 제목 글자가 있는 줄만 책으로 잡힙니다.
2. **책등 분할** — 열마다 세 가지를 잽니다.
   - **가장 긴 연속 세로 에지**: 책 경계는 위아래로 길게 이어지고 글자 획은 짧게 끊깁니다.
     기울기는 열마다 따로 찾습니다. 원근 때문에 왼쪽 책과 오른쪽 책이 서로 다르게 기웁니다.
   - **대표 색 변화**: 밝기가 비슷한 두 책(파랑 옆 초록)을 갈라 줍니다. 대표 색은 평균이
     아니라 중앙값입니다. 평균을 쓰면 큰 글자가 지나가는 열이 통째로 어두워집니다.
   - **책 사이 그림자**: 빽빽한 책장에서는 이게 가장 또렷한 단서입니다. 열의 **밝은 쪽
     밝기(70번째 백분위)**가 주변보다 얼마나 낮은지로 잽니다. 중앙값을 쓰면 제목 글자가
     굵은 열이 그림자만큼 어둡게 나와 한 권이 둘로 쪼개집니다.

   세 신호를 합친 뒤, 위아래로 이어진 세로선이 약한 봉우리는 깎습니다. 책등 음영이 꺾이는
   자리나 쌓인 제목의 좌우도 색이 바뀌고 어둡지만, 두 책이 맞닿은 자리와 달리 세로선이 없습니다.
3. **문턱 대신 국소 대비** — 사진 한쪽만 그늘지면 절대 점수는 통째로 낮아집니다. 주변
   기준선보다 얼마나 솟았는지로 고릅니다. 먼저 또렷한 경계만 세어 **대표 두께**를 잡고,
   그 두께를 최소 간격으로 삼아 다시 고릅니다. 책 다섯 권짜리 칸과 마흔여섯 권짜리 칸에
   같은 값을 쓸 수 없기 때문에, 고정 비율 대신 사진마다 두께를 재서 맞춥니다.
4. **넓은 구간 쪼개기 / 쪼개진 것 도로 붙이기** — 한 책장에 꽂힌 책은 두께가 비슷합니다.
   유난히 넓으면 경계를 놓친 것으로 보고 안쪽에서 나눕니다. 반대로 한 권이 둘로 쪼개진
   자리는 두 조각의 바탕색이 같고 그 자리에서 색이 뚝 바뀌지도 않습니다. 그런 짝은 도로 붙입니다.
5. **기울기 펴서 잘라내기** — 밴드마다 그 책이 기운 만큼 크롭을 같이 기울여 폅니다.
   얇은 책은 사진 가로의 2%도 안 되는데, 2도만 기울어도 세로로 자르면 옆 책이 통째로
   딸려 들어옵니다. 책이 차지하는 위아래 범위도 밴드마다 따로 찾아 자릅니다.
6. **세 가지로 읽기** — 돌려 세운 두 방향(위→아래, 아래→위)과, 한국 책에 흔한
   **세로로 쌓은 글자**용으로 돌리지 않은 크롭을 세로 전용 모델(`kor_vert`)로 읽습니다.
   앞의 네 권으로 방향이 정해지면 나머지는 그 방향만 읽습니다. 잘 안 읽히는 책(거꾸로 꽂힌
   책 등)만 그때 세 방향을 다 봅니다. 마흔 권짜리 칸에서 읽는 시간이 3분의 2로 줍니다.
7. **제목 줄만 남기기** — 책등에는 제목 말고도 출판사 이름, 시리즈 번호, 지은이, 분류가
   잔글씨로 찍혀 있습니다. 전부 이어 붙이면 "ChildApple 드림 28 곰이의 카레라이스 건강과 안전"
   이 되고, 잔글씨를 길게 오독한 쪽이 점수까지 이겨 읽기 방향마저 틀립니다. 사람이 제목을
   알아보는 방식 그대로, **눈에 띄게 큰 줄**만 남깁니다. 크기는 낱말이 아니라 줄 상자로
   잽니다. 라틴 문자는 "and"처럼 삐침 없는 낱말의 상자가 "Thinking"의 절반밖에 안 됩니다.
8. **읽기 고르기** — 페이지 전체 신뢰도는 거꾸로 읽은 글자에도 높게 나와 못 믿습니다.
   글자 수로 가중한 단어 신뢰도에 기호 범벅과 짧은 결과를 깎아 고릅니다. 이때 한글 음절은
   자모 두세 개가 모인 글자라 라틴 한 글자보다 무겁게 셉니다. **한글 한 글자도 한 낱말로
   셉니다.** 세로로 쌓인 제목은 음절 하나씩 떨어져 나오는데, 두 글자 미만을 버리면 제대로
   읽은 결과가 통째로 0점이 되어 라틴 잡동사니에 집니다.
   진 후보들도 남겨 두어, 화면에서 "다르게 읽기"를 눌러 바꿔 끼울 수 있습니다.
9. **다듬기** — 군더더기 토막을 먼저 걸러낸 뒤에 붙입니다. 먼저 붙이면
   "2#.배고픈늑대와…"처럼 기호까지 제목에 눌어붙습니다. 한글이 대부분인 읽기에서는
   옆 책에서 넘어온 라틴 문자 쪼가리를 버립니다.
10. **제목 보정** — Open Library에서 찾아 정식 제목과 표지를 붙입니다.
    네트워크가 막혀 있으면 이 단계만 조용히 건너뜁니다.

책등을 나누지 못하면 사진 전체를 세 방향으로 읽어 줄 단위로 건지는 방식으로 물러섭니다.

## 정확도

### 실제 사진

실제 책장 사진 한 장(2576×1932, 얇은 아동서 약 46권이 한 칸에 빽빽하게)으로 잰 값입니다.

| | 고치기 전 | 고친 뒤 |
| --- | --- | --- |
| 찾은 권수 | 11권 | 46권 (실제 약 46권) |
| 알아볼 수 있는 제목 | 0권 | 14~15권 |

고치기 전에는 밴드 하나에 책이 서너 권씩 들어가 `SS S BREE 3 불 기 fs grit a EY E NG`
같은 것이 나왔습니다. 원인은 세 가지였습니다.

- **분석 해상도가 모자랐습니다.** 책등 하나가 사진 가로의 2%도 안 되는데 작업 캔버스를
  2000px로 줄이면 책등이 20px 남짓이라 한글 획이 뭉개집니다. 3600px로 올렸습니다.
- **최소 책등 두께가 실제 책등보다 두꺼웠습니다.** 고정 비율(2.5%)로 잡던 것을 사진마다
  대표 두께를 재서 정하도록 바꿨습니다. 밴드 수 상한도 24에서 80으로 올렸습니다.
- **세로로 자르고 있었습니다.** 원근 때문에 왼쪽 책과 오른쪽 책의 기울기가 다른데 전체에
  한 각도만 썼고, 크롭은 아예 기울이지 않았습니다. 열마다 기울기를 찾고 크롭도 폅니다.

### 해상도가 곧 정확도

같은 사진을 줄여 가며 재 봤습니다. 정답 제목의 **연속 여섯 글자가 읽기에 그대로 들어 있으면
찾은 것**으로 셉니다.

| 사진 크기 | 책등 두께 | 찾은 제목 |
| --- | --- | --- |
| 2576px (원본) | 약 48px | **11 / 37** |
| 1288px (절반) | 약 24px | 4 / 37 |
| 860px (3분의 1) | 약 16px | 0 / 37 |

책등 두께가 절반이 되면 읽히는 제목이 3분의 1로 떨어집니다. 이 구간에서는 후처리로
살릴 수 있는 것이 거의 없고, **한 권에 몇 화소가 실렸는지**가 거의 전부를 결정합니다.
그래서 작업 캔버스 한도를 3600px로 올려 휴대폰이 준 화소를 버리지 않게 했습니다.
경계 찾기는 어차피 1500px로 줄여서 하고 잘라낸 책등도 목표 너비에 맞춰 다시 키우므로,
이 값을 올려도 인식 시간은 거의 그대로입니다.

같은 이유로 **나눠 찍기**를 붙였습니다. 다만 한 가지는 분명히 해 둘 필요가 있습니다.
이미 찍은 사진을 잘라 나누는 것은 **효과가 없습니다.** 실제로 원본을 좌우 절반으로 잘라
따로 읽혀 보니 11개에서 8개로 오히려 줄었습니다. 잘라도 한 권에 실린 화소는 그대로이고,
선반 위아래 맥락만 없어져 경계 찾기가 나빠집니다. 효과는 **더 가까이 가서 새로 찍을 때만**
납니다. 그래서 안내 문구도 "나머지를 가까이에서 찍으면"이라고 적습니다.

(가까이 찍었을 때의 이득은 위의 줄이기 실험에서 거꾸로 미루어 본 것이고, 실제 근접 촬영
사진으로는 아직 재지 못했습니다.)

### 한 장에 몇 권까지?

"몇 권"은 사실 잘못된 단위입니다. 정확도를 결정하는 것은 권수가 아니라 **책등 하나에
실린 화소 수**입니다. 두꺼운 책 서른 권과 얇은 책 서른 권은 전혀 다릅니다.
그래서 앱은 권수 대신 책등 굵기를 기준으로 삼고, 그 기준을 **기기마다 다시 계산**합니다.

```
한 장에 담을 권수 = 사진 가로 화소 × 0.85 ÷ 80
```

- `0.85` — 잘 찍어도 양옆에 책장 벽이 조금 남습니다.
- `80` — 목표 책등 굵기(px). 근거는 아래에 적었습니다.

| 카메라가 주는 가로 | 한 장에 |
| --- | --- |
| 1280px | 13권 |
| 1920px | 20권 |
| 2576px (예시 사진) | 27권 |
| 3840px | 40권 |

앱은 이 값을 **직접 재서** 씁니다. 촬영 화면에서는 카메라가 실제로 주는 해상도
(`video.videoWidth`)로 계산해 "한 번에 20권까지"라고 미리 알려 주고, 찍은 뒤에는 그 사진에서
책등이 실제로 몇 px이었는지 재어 "책등이 34px로 얇아요. 3번에 나눠 찍어 주세요"라고 알려 줍니다.
찍고 난 뒤의 값이 더 믿을 만합니다. 예측이 아니라 그 사진에서 실제로 나온 값이기 때문입니다.

**80px의 근거와 한계.** 실제 사진에서 잰 값은 48px에서 11/37, 24px에서 4/37, 16px에서 0/37
입니다. 48px 위쪽은 원본 해상도가 거기까지라 **재지 못했습니다.** 80px은 거기에 더해,
tesseract 한글 모델이 글자 높이 35~45px에서 가장 잘 읽고 제목 글자가 책등 너비의 3분의 2쯤을
차지한다는 점에서 잡은 목표치입니다. **재서 확인한 값이 아닙니다.**

합성 사진으로는 이 기준을 정할 수 없었습니다. 합성 책등은 제목 글자가 책등 폭을 꽉 채우고
대비도 완벽해서, 책등 24px에서 200px까지 정확도가 거의 변하지 않습니다 (한글 가로 7~8/10).
실제 사진에는 출판사 잔글씨, 여백, 흐림, 반사, 굽은 책등이 있어 훨씬 일찍 무너집니다.
합성 벤치는 분할 회귀를 잡는 데는 쓸모가 있지만, **촬영 기준을 정하는 데는 못 씁니다.**

```bash
node bench/run.mjs --dsf 5 --width 626   # 책등 61px로 줄여서 재기 (해상도 스윕용)
```

### 남은 제목 품질

제목이 아직 완벽하지는 않습니다. 잘 나온 예는 `빙그레섬의찍찍대원들`, `배고픈늑대와잘난척다조`,
`아주탁은고래의믿기힘든이야기`, `눈아래사는친구들`, `알쌍달씬기한착시놀이잘봐` 처럼
읽고 고칠 수 있는 수준이고, 절반 넘는 책등은 여전히 못 읽습니다. 실제 책등이 원본에서도
30~40px밖에 안 되는 것이 근본 한계입니다. 권수와 순서가 맞으므로 손으로 고칠 자리는 남습니다.

### 합성 사진

`bench/`에 측정 코드가 들어 있어 그대로 재현할 수 있습니다. 조건을 통제한 이미지
(1.2도 기울임, 사진처럼 흐리게 처리, 명암 불균일)를 만들어 씁니다.

두 가지를 따로 셉니다. **바로**는 화면에 처음 뜨는 제목이 맞은 권수,
**후보 포함**은 "다르게 읽기"를 한 번 눌러 도달할 수 있는 것까지 셈한 권수입니다.

| 책장 | 바로 | 후보 포함 | 글자까지 정확 |
| --- | --- | --- | --- |
| 영문 · 돌린 글자 (10권) | 8 | 9 | 6 |
| 한글 · 돌린 글자 (10권) | 7 | 7 | 7 |
| 한글 · 세로로 쌓은 글자 (8권) | 6 | 6 | 6 |

**글자까지 정확**은 제목이 한 글자도 틀리지 않은 권수입니다. 찾아낸 제목들의 평균 글자
오류율은 영문 1%, 한글 0%입니다. 실제 사진에 맞춰 고치기 전에는 9 / 7 / 4권이었습니다.
영문이 한 권 줄고 한글 세로가 두 권 늘었습니다. 한글 세로가 는 것은 **한글 한 글자도
한 낱말로 세도록** 점수를 고친 덕입니다. 그 전에는 세로로 쌓인 제목을 제대로 읽고도
음절이 하나씩 떨어져 나와 0점을 받아, 거꾸로 읽은 라틴 잡동사니에 지고 있었습니다.

```bash
npm run dev                                   # 한 터미널에서
node bench/run.mjs                            # 다른 터미널에서
node bench/run.mjs --case ko-stacked          # 한 가지만
node bench/segment.mjs bench/.cache/ko-stacked.png   # 책등 분할만 눈으로 확인 (경계선 그린 이미지)
node bench/read.mjs ~/사진.jpg                # 실제 사진을 앱과 똑같이 읽어 결과만 출력
node bench/crops.mjs ~/사진.jpg bench/.cache/crops 0 12   # 잘라낸 책등을 눈으로 확인
```

`bench/read.mjs`와 `bench/crops.mjs`는 정답이 없는 **실제 사진**을 검토할 때 씁니다.
분할이 맞았는지(`segment.mjs`의 경계선 이미지), 크롭이 옆 책을 물고 있지 않은지(`crops.mjs`),
그래서 무엇이 읽혔는지(`read.mjs`)를 차례로 봅니다.

`bench/flow.mjs`는 정확도가 아니라 **시나리오대로 도는지**를 봅니다. 휴대폰 폭(420px)에서 돌고,
매번 "앱을 열고 첫 칸이 채워질 때까지 몇 번 눌렀는지"를 찍어 UX 개선을 숫자로 남깁니다.
`docs/시나리오.md`의 완료 기준을 그대로 확인합니다. Chromium의 가짜 카메라에 합성 책장
영상을 물려, 책장 설정부터 칸 선택, 촬영, 순서 반영, 순서 바꾸기, 다시 찍기, 칸 수 바꾸기,
책장 추가, 새로고침 후 유지까지 실제로 조작합니다 (15가지).

```bash
npm run build && npm run preview              # 한 터미널에서
node bench/flow.mjs                           # 다른 터미널에서 (17가지 점검 + 누름 횟수)
node bench/copy.mjs --verbose                 # 화면에 적힌 설명 글자 수
```

남은 한계:

- 짧은 제목("총 균 쇠")이나 좁은 책등은 아직 놓칩니다.
- 두께가 비슷한 책이 이어지면 경계를 잘못 잡아 두 제목이 한 줄로 섞일 때가 있습니다.
- 글자가 작거나 가려진 책등, 반사가 심한 표지는 놓칩니다.
- **Open Library는 맞춤법을 고쳐 주지 못합니다.** 낱말 검색이라 "Refactorin"처럼 한 글자만
  틀려도 아무것도 찾지 못합니다 (퍼지 검색도 없습니다). 제목이 이미 맞을 때 정식 표기와
  표지·ISBN·연도를 붙여 주는 역할입니다. 한국어 도서는 수록이 고르지 않아 더 자주 비어 있습니다.
- 한 칸에 마흔 권이 넘게 꽂힌 실제 사진에서는 권수와 순서는 맞지만 제목은 절반 넘게
  못 읽습니다. 책등이 원본에서도 30~40px라 한글 획이 뭉개지는 것이 근본 한계입니다.
  나눠 찍기로 늘릴 수 있지만, 실제 근접 촬영 사진으로는 아직 재지 못했습니다.
- **목표 책등 굵기 80px은 재서 확인한 값이 아닙니다.** 실제로 잰 것은 48px 이하뿐이고
  (48px에서 11/37), 그 위는 원본 해상도가 모자라 재지 못했습니다. 근접 촬영 사진이 생기면
  다시 재야 합니다.
- 실제 휴대폰 카메라로는 확인하지 않았습니다. 위 점검은 가짜 카메라 장치를 씁니다.
  촬영 화면이 실제 기기에서 몇 px을 받는지도 확인하지 못했습니다.
- 실제 사진 수치는 사진 한 장으로만 잰 것입니다. 개인 사진이라 저장소에 넣지 않았습니다.

### 잘 찍는 요령

- 책장 한 칸이 화면에 꽉 차게, 정면에서 찍습니다. 멀리서 전체를 담으면 글자가 뭉갭니다.
- **한 장에 담을 권수는 기기마다 다릅니다.** 촬영 화면이 "한 번에 n권까지"라고 알려 줍니다.
  그보다 많으면 [이어서 찍기]로 나눠 찍습니다. 방금 찍은 곳 다음부터, 한두 권만 겹치게
  가까이에서 찍으면 됩니다. 이음매에서 제목이 똑같은 책은 앱이 한 권만 남깁니다.
- 책등에 그림자나 반사가 생기지 않게 합니다.
- 이미 찍은 사진을 잘라 나누는 것은 소용없습니다. 카메라를 가까이 가져가야 화소가 늡니다.

## 성능

책 수에 비례해 시간이 듭니다. 데스크톱에서 열 권 남짓이면 몇 초, 마흔여섯 권이 빽빽한
칸은 2분쯤 걸립니다. 휴대폰에서는 그보다 더 걸립니다. 앞의 네 권으로 읽기 방향이 정해지면
나머지는 한 번씩만 읽으므로, 방향을 정하지 않을 때보다 3분의 2 시간으로 끝납니다.
읽는 중에도 진행 상황(n/46권)이 보이고 언제든 취소할 수 있습니다. 언어 데이터는 처음 한 번만 받아 캐시합니다.
"영어만"으로 두면 눈에 띄게 빨라집니다.
